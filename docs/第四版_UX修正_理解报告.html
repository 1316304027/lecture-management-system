一、核心原则 — 你必须先懂这个

这次修改的本质不是「换皮肤」，而是信息架构：每个画面只干一件事，不重复、不绕路。

画面干什么比喻
実績レポート看数字：出席率、提出率、平均分成绩单
ユーザー管理管账号：创建、编辑、看详细プロフィール人事档案室
教材 / 課題管 PDF 和作业，设置是否对学生显示教务资料柜
お知らせ讲师发文字通知，学生在コースポータル看班级公告栏
必须掌握（中文）：列表页只展示汇总数据和小头像；学生的完整资料只在「ユーザー管理」里打开。实绩报告不再有「プロフィール」按钮。
日语 · 发表必背（20秒）
実績レポートは成績の一覧用です。受講者の詳細プロフィールは、ユーザー管理に集約しました。一覧では識別用にアバターのみ表示します。

二、修改1：「公开课」误解 — 文案改正

发生了什么？

画面上有「公開課題数」「公開中」，容易被理解成「对外公开的课程」。
实际含义：讲师已对学生开放可见的课题/教材（数据库字段 published = true）。

技术本质（面试用）

  • 实体：Material.published、Assignment.published（布尔值）
  • 统计：ReportService 调用 countByCourse_IdAndPublishedTrue
  • 学生端：Repository 只查 published = true 的记录

文案对照

位置旧新
实绩报告统计卡公開課題数課題数（受講者公開済）
教材状态公開中表示中
上传选项即時公開アップロード後すぐ受講者に表示
课题列头公開状態受講者への表示

请求链路（背一条）

讲师勾选「表示する」→ POST toggle
  → MaterialService 修改 published
  → PostgreSQL (RDS)
学生打开教材页 → 只查询 published=true
日语 · 15秒
「公開」は外部公開ではなく、受講者に教材や課題を表示するかどうかの設定です。非表示の資料は学生画面には出ません。
日语 · 社长追问
Q: 公開と非公開の違いは？
A: 講師が受講者に見せるかどうかのフラグです。DB の published カラムで管理しています。

三、修改2：プロフィール — 只从ユーザー管理进

以前的问题（你截图里的）

  • 实绩报告 + 用户管理 两处都有「プロフィール」按钮
  • 从实绩报告点进去，返回却写死「← ユーザー管理」→ 导航混乱

现在的规则

页面显示什么能进详情吗？
実績レポート头像 + 姓名 + 出席/提出/分数❌ 不能
ユーザー管理头像 + 列表 + 操作按钮✅ 受讲者有「プロフィール」

技术链路 A — 实绩报告（只有头像）

GET /admin/reports?courseId=1
  → AdminController.reports()
  → ReportService.getCourseReport()        // 算出席率、提出率、平均分
  → ProfileService.buildAvatarUrlMap()     // 批量生成 S3 头像 URL
  → admin-reports.html 渲染（无プロフィール按钮）

技术链路 B — 用户详情

GET /admin/accounts/{userId}/profile
  → AdminController.userProfile()
  → ProfileService.getAvatarUrl(user)
  → fragments/profile-card.html
  → returnUrl = /admin/accounts（返回用户管理）

头像为什么全站通用？

  • users 表字段 avatar_s3_key 存 S3 路径
  • ProfileService.getAvatarUrl() 生成临时读 URL（Presigned GET）
  • buildAvatarUrlMap() 给列表页批量生成，避免重复查询
日语 · 必背
プロフィール詳細はユーザー管理からのみ開けます。実績レポートでは識別用にアバターを表示しますが、詳細画面には遷移しません。
日语 · 追问：照片存在哪？
S3 に保存し、DB にはキーのみ保持します。表示時に Presigned URL を発行します。

四、修改3：お知らせ — 从教材页拆出

为什么拆？

以前公告塞在教材管理页面最底下，和 PDF 上传混在一起，职责不清。

现在的 URL 分工

URL谁用干什么
/instructor/materials?courseId=讲师只管 PDF 教材
/instructor/announcements?courseId=讲师发帖 + 历史列表
POST /instructor/announcements讲师提交后写 DB，跳回公告页
/student/course?courseId=学生コースポータル，只读公告

完整链路（Demo 讲这条）

讲师填标题+内容 → POST /instructor/announcements
  → InstructorController.postAnnouncement()
  → AnnouncementService.create()   // 校验是否担当该课程
  → INSERT course_announcements
  → redirect /instructor/announcements?courseId=

学生打开コース詳細
  → StudentController.coursePortal()
  → announcementService.getByCourse()
  → student-course-portal.html

数据表：course_announcements（course_id, title, content, created_at, author_id）

讲师主页按钮（7个）

教材管理 | 課題管理
提出確認 | 出欠確認
受講者一覧 | お知らせ
チャット（未読バッジ）
日语 · 15秒
お知らせ機能を教材管理から分離し、専用画面で投稿・管理できるようにしました。受講者はコースポータルで閲覧します。

五、修改4：日期 — 年/月/日下拉框

问题

<input type="date"> 各浏览器样式不同，和全站绿色主题不统一。

实现

  • 片段文件：fragments/date-picker.html
  • 三个下拉：lessonYear / lessonMonth / lessonDay
  • 后端：AdminController.parseDate() → LocalDate.of(年,月,日)
  • 样式：pcfa-date-picker（与时刻选择 pcfa-time-picker 一致）
管理员选 2026年6月24日 → POST /admin/courses/{id}/schedule/add
  → parseDate() → LocalDate
  → CourseScheduleService.addSchedule()
  → course_schedules 表
日语
授業日の入力は、ブラウザ標準の日付ピッカーではなく、年・月・日のドロップダウンに統一しました。時刻入力と同じ UI 方針です。

七、修改6：採点待ち — 分数不能显示 0

业务规则：学生已提交、讲师未批改 → 不能算 0 分。

  • ReportService.calcGradedAverage() 只平均 score IS NOT NULL 的提交
  • 若一条都没批改 → averageScore = null → 画面显示「採点待ち」徽章
日语 · 必背
未採点の提出は平均点に含めません。採点が完了するまでは「採点待ち」と表示します。0点として扱いません。

十、Q&A 卡片 — 社长可能问的 10 题（日语参考答案）

1. このシステムの目的は？

講師・受講者・管理者の三役割で、出席・教材・課題・チャットを一元管理する受講管理システムです。

2. なぜプロフィールをユーザー管理に集約？

実績レポートは数値確認用、ユーザー管理はアカウント管理用と役割を分け、画面遷移の混乱を防ぐためです。

3. 「公開」の意味は？

受講者に教材や課題を表示するかどうかの設定であり、コースを外部公開する機能ではありません。

4. ファイルはどこに保存？

RDS にメタデータ、PDF や画像は S3 です。大きいファイルは Presigned URL でブラウザから直接 S3 にアップロードします。

5. チャット未読はどう実装？

chat_read_status テーブルで最終既読時刻を管理し、未読件数をホームにバッジ表示します。

6. 平均スコアが0にならない理由は？

未採点を0点として平均に入れると誤解を招くため、採点済みのみ平均し、それ以外は「採点待ち」です。

7. お知らせと教材の違いは？

教材は PDF 資料、お知らせは講師から受講者へのテキスト連絡です。画面も DB も分けています。

8. デプロイ環境は？

AWS EC2 上の Docker で Spring Boot、DB は RDS PostgreSQL、ファイルは S3 です。

9. AI で作ったのか？

Cursor を補助ツールとして使いましたが、要件の整理、動作確認、AWS デプロイ、不具合修正は自分で行いました。設計の意図は説明できます。

10. 今後の改善（7月）？

UI の継続改善、テスト自動化、必要に応じて Cognito による認証強化などを検討しています。
